# 原生 Android 与 XHyper 上层对比测试设计

日期：2026-10-08。状态：采集、观察和分析模块已实现，全套串行链路正在实机验证，正式 A/B 尚未执行。

2026-10-08 更新：亮屏功耗及活动内存优先采用 Perfetto 官方数据源和 Trace Processor，shell 采样降为备用。T11206 当前 PowerStats 示例服务的轨能量、消费者和状态驻留属于模拟数据，不能纳入真实对比。启动复用现有 bootstat、getprop 和 logcat 记录。细节见 [成熟工具选择](MATURE-TOOLS.md)，一般供电与统计约束继续适用。

## 1. 目标与职责

本框架比较同一设备、同一 Android 和宿主内核在原生运行及搭载 XHyper 时的差异。它接收镜像负责方提供的启动镜像、二进制身份、正常配置证据和切换后读回证据，不构建或刷写镜像。

执行方必须区分“镜像身份已经确认”和“模式已经在设备上启动”。Android 的单个空属性不能证明没有虚拟化层；命令行里的重复参数也需要结合实际解析及运行证据。镜像清单、启动标识、运行时内核标识和模式确认记录共同约束每轮样本。

正式分数来自双方约定的正常配置。增加的诊断计数、周期打印、持续跟踪或锁监视会改变测量条件，必须单独报告。已经随正式提交存在的机制也要由镜像负责方明确配置；框架不能自行改动 XHyper 源码来获得计时数据。

## 2. 主要指标与工具

| 项目 | 工具和主要输出 | 最低有效重复 |
|---|---|---:|
| 启动 | 控制端单调时钟、新启动标识、Android 启动事件；分别记录连接恢复、系统完成和桌面就绪。 | 每侧 3 次正常重启，优先 5 次。 |
| 中央处理器性能 | 现有 Geekbench 6 同版安装包；单核、多核总分及全部子项。 | 每侧 3 次，尽量来自 3 次不同开机。 |
| 图形处理器计算性能 | Geekbench 6 双方共同可用的 Vulkan 接口；总分、API 和全部子项。 | 每侧 3 次，OpenCL 单列为可选项。 |
| 图形渲染补充 | 优先使用现有浏览器的固定本地滚动及 Canvas/WebGL 工作负载，并记录系统帧统计；3DMark 仅在已安装且资源齐全时使用。 | 每侧 3 次；不能完成则如实标注缺项。 |
| 基准运行能耗 | 与中央处理器、图形处理器测试同步进行设备内采样，报告整段能耗和平均功率。 | 与各次有效基准对应。 |
| 亮屏静置 | 固定主屏幕、亮度设置和刷新率；内部计量连续采样及累计量核验。 | 每侧 2 个独立 8 分钟窗口。 |
| 熄屏待机 | 累计电荷或能量端点、实际经过时间及系统休眠证据。 | 每侧 2 个 15–20 分钟窗口。 |
| 内存占用 | `/proc/meminfo`、压缩交换内存统计及窗口外 Android 进程内存统计；区分稳定基线、活动期间和负载后。 | 每侧至少 3 次开机基线，每个基线 3 个轻快照。 |
| 日常使用补充 | 已有本地视频、固定滚动及应用切换、低音量音频；固定文件和操作次数。 | 主项目完成后每侧 1 次 12 分钟序列。 |

Geekbench GPU 测的是计算负载，渲染补充单列，不能把界面帧率当成纯 GPU 跑分。固定网页属于浏览器、处理器、图形驱动和系统调度的综合场景。3DMark 可用时单独记录其标准负载和版本。[Geekbench 官方 GPU 工作负载](https://www.geekbench.com/doc/geekbench6-gpu-compute-workloads.pdf)与 [Wild Life 官方说明](https://support.benchmarks.ul.com/support/solutions/articles/44002135593)定义了两类负载的不同范围。

本轮无外部仪器的启动主项是“正常重启到 Android 可用”。它包含重启、引导及系统启动的代理时长，不能命名为完全断电后的冷启动。桌面终点需要本机桌面、解锁及绘制证据；如果适配未完成，先报告系统完成和设备内阶段，将桌面就绪留为空值及原因。

## 3. 四阶段实验

在计分前固定原生→XHyper→XHyper→原生的顺序；设备若已处于待测 XHyper 正式镜像，可以完全反转。四阶段基准次数依次为 1、1、2、2，因此每侧各 3 次。后两个阶段的第二次正式 CPU/GPU 运行前安排同模式重启，从而取得每侧至少 3 个开机样本。模式切换后首次启动带 `post_flash_boot` 标签，启动统计同时报告包含和排除该类样本的结果。

每阶段在环境稳定后先取得静置及待机窗口，再进行计算负载。运行间采用相同温度条件恢复，不用固定 60 秒替代冷却验证。每次性能运行需要开机至少 300 秒，并核对后台任务。运行造成的自然升温、降频和功耗变化属于被测行为，保留为结果；运行前遗留热状态不匹配则单独标注。

本轮统一配对起始条件：电池温差不超过 1.5 °C，主要处理器温差尽量不超过 3 °C，电量差尽量不超过 5 个百分点。它们是本次协议阈值，不是厂商安全规格。细项方法文档中的建议值以本节统一协议为准。正式放电测量尽量在 35%–80% 电量进行；当前满电读数需要先验证累计计量在离开满电后的行为，不能用人为修改电量上报值解决。

两侧固定 Android 指纹、宿主内核及模块、应用包哈希、数据、亮度设置、刷新率、网络、音量、充电策略和后台应用。保留正常调频、核心在线和温控。执行方在调整前记录设置原值及恢复方法；本次只读预检不会修改这些设置。

## 4. 功耗能力决定结论范围

能力门槛先于正式计量。先探测电池即时电流、累计电荷、累计能量、输入遥测及电源轨，然后验证单位、符号、实际刷新率、量化步进、负载响应和累计计量稳定性。标准 Linux 属性使用微伏、微安及微安时，但自定义节点需另证。[Linux 电源接口说明](https://www.kernel.org/doc/html/latest/power/power_supply_class.html)

若软件输入暂停确实使所有外部输入断开，且有实际遥测与电池响应证据，报告可以使用“电池侧整机平均功率”和“任务能耗”。仅停充、输入限流设置、`online` 标志或 `dumpsys battery unplug` 不能证明这个供电边界。该命令可能仅改变系统上报状态；执行者应核对实际平台实现。[Android 电池服务](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/BatteryService.java)

无法证明完全电池供电时，工具仍保留带符号的“电池净能量变化”，或明确覆盖范围的硬件电源轨能耗。部分轨、充电器额定值、输入限流和系统模型均不能自动填入整机功耗栏。框架应明确报告“当前条件无法获得整机功耗”，同时完成其他性能项目。

即时采样在设备本地进行，Perfetto 请求每秒一次；辅助温度每 5 秒一次。请求频率需要与实际时间戳核对。备用 shell 脚本的间隔参数是读取后的等待时间，本机快测实际间隔接近两秒。读取起止时间揭示非同时采集的误差，分析器保留耗时并支持拒绝门槛。使用包含系统休眠的设备时钟，禁止跨重启积分。备用脚本采用 `/proc/uptime`，需要执行方核对本机语义、0.01 秒量化和读取开销，分析器使用实际时间差而非预定间隔。该脚本没有申请唤醒锁，也不适用于测量深度待机。

熄屏待机使用经过验证的累计端点，窗口中停止 ADB 轮询和周期采样。设备内闹钟若没有适配，可以由执行方在结束时唤醒并立即读取端点，使用真实经过时间并标注终点唤醒开销。只有核实系统休眠累计量或计数后才能叫“深度待机”；没有该证据时称为“熄屏静置”。USB 本身的电源管理影响属于限制。

## 5. 采集状态和运行目录

每个运行使用独立目录和编号。状态依次为 `prepared`、`started`、`computing`、`compute_complete`、`result_pending`、`persisted`、`exported`、`validated`。运行失败转为 `failed`，原始证据保留；结果未上传或持久化不等于计算失败。

```text
runs/<campaign>/
  campaign.json
  image-manifests/
  preflight/<mode>/
  boots/<boot_id>/events.jsonl
  runs/<run_id>/
    run.json
    events.jsonl
    environment-before.json
    environment-after.json
    samples.csv
    history/                 # 一致性 SQLite 快照及日志文件
    result.json              # 完整原始 Geekbench 文档
    screenshots/
    analysis.json
  metric-rows.json
  comparison.json
  report.md
```

写入必须先落临时文件、完成后改名；运行目录不复用。失败、跳过、超时和未实现能力均保留原因，不写零值。结果导入器读取一致性数据库并保留完整 JSON；它不负责把所有历史结果自动绑定到当前开机。执行方需要依据开始前文档号、UUID、当前运行事件及版本明确绑定。

计算功耗窗口和 Geekbench 内部 `runtime` 分开记录。上传及存储等待不属于计算窗口。JSON 的 `clock` 未校准前不能直接映射到设备时间；子项分数全部导出，子项能耗暂不计算。无法准确定位计算边界时，使用带误差区间的完整生命周期能耗，名称必须说明其中包含点击及观察延迟。

## 6. 分析和报告

统计以完整运行及开机为单位，按应用版本、API、负载、供电边界和配置分别分组。报告样本数、独立开机数、全部值、均值、中位数、标准差、范围和差异百分比。少量样本的范围不是置信区间；默认分析器不输出显著性或虚假的 95% 区间。

报告同时列出基准分数、运行时长、平均功率和总能耗，避免把低功率但更久的运行解释为节能。检查原生前后阶段的漂移；漂移与模式差异同量级时，报告明确混杂因素。重复波动、窗口不确定性或计量分辨率大于差异时，使用“本轮没有分辨出差异”。

正文至少有启动、CPU、GPU、CPU/GPU 运行功耗、静置/待机、内存占用和可选日常序列七组结果。每行附样本数、来源、计量边界和限制。未测项目明确写未完成及原因。本仓库当前只有框架验证与设备预检，没有本轮 A/B 实测结果。

内存主项记录开机稳定后的可用内存和 `MemTotal - MemAvailable` 的估算不可用量，并列缓存、内核、压缩交换及进程统计。活动期间每 5 秒取得轻量读数，最低可用内存只称“采样最低值”；完整进程统计放在功耗窗口之外。三次同开机快照属于一个基线，不构成三次独立实验。两侧 `MemTotal` 差值仅表示 Android 可见内存变化；虚拟化层自身静态及动态保留区需要镜像负责方交付分区及分配证据，无法证明时保留为未知。

## 7. 参考工具状态

只读 `doctor`、镜像清单验证、SQLite 结果导入、离线电流积分、端点法、内存快照解析和分组统计已提供参考实现。离线工具通过已知量值与必须拒绝输入检查；执行前仍需验证实际平台接口。`device/sample-battery.sh` 需先在亮屏静置中核对低开销及负载响应，两侧使用同一脚本。

启动事件观察器、Geekbench 按钮定位及稀疏计算状态观察、单启动结果绑定、屏幕窗口和自动恢复已实现。启动的桌面首次绘制仍需额外证据；稀疏观察不能产生精确的瞬时计算终点。输入供电控制和待机闹钟尚未适配；熄屏窗口由控制端定时结束并记录唤醒开销。框架不写入未知电源控制节点。运行顺序、时间受限策略和实际验证状态分别见 `AUTOMATION.md` 与 `PLAN-20261008.md`。
