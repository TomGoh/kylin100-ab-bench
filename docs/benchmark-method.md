# 原生 Android 与 XHyper：启动和性能测试方法设计

> 2026-10-08 整合说明：本文件提供详细方法；起始温差、四阶段次数、可选负载及截止时间以 [总体设计](DESIGN.md)和[本轮计划](PLAN-20261008.md)为准。方法建议不表示本机能力已经验证。

日期：2026-10-08。状态：**设计完成，未执行设备测试。**

本方案只负责上层测试、结果采集和统计。Claude Code 提供两侧镜像、切换方法和镜像身份证据；本方案不构建镜像，也不改变产品代码、启动分区或硬件。测试对象是同一台 T11206HXH6600007 平板。设备序列号、Android 版本、应用版本和实际镜像身份必须在执行时重新核对。

## 1. 两侧必须满足的条件

执行方把原生 Android 定义为 A，把搭载 XHyper 的 Android 定义为 B。A 必须通过实际启动参数及镜像来源确认没有运行其他虚拟化层；不能只凭界面上显示“native”判断。共享记忆记载该平板原厂使用 `kvm-arm.mode=none`，这只是预检线索。

两侧必须使用同一份 Android 数据、宿主内核、模块、应用安装包、应用数据、驱动和电源设置。执行方需提供宿主内核的二进制哈希与运行时构建标识、Android 构建指纹、镜像哈希、实际启动槽位及启动后读回证据。A 和 B 整个启动镜像的哈希必然不同，不能把这一点当成宿主内核不一致。框架还应记录命令行中不可避免的差别。

B 的计分镜像必须来自没有未提交修改的正式提交，使用双方约定的正常配置，并关闭诊断计数、周期打印、黑匣子和锁监视等计时干扰。测试日志可以由 Android 层采集，不能为了获得这些日志而更改 XHyper。若执行方只能提供带诊断的镜像，报告必须把它单列为“诊断配置对比”，不能冒充正式镜像性能。

两侧都保留系统正常调频、调压和热管理。框架不得关闭热保护、强制所有核心满频、改变空闲策略或用降温硬件。框架先核对是否遗留了调频下限、内存场景加速、后台虚拟机或持续跟踪；发现人为设置时，由执行方恢复约定设置并记录。该平板的 Linux 源码在本工作区不可用，框架只能依据设备的 `/proc`、`/sys`、实际镜像和运行证据解释它的行为。

固定项目包括亮度、屏幕分辨率与刷新率、旋转方向、系统性能模式、电量区间、充电状态、网络连接、蓝牙状态、声音、屏幕超时及后台应用。框架先保存设置，再在两侧采用相同值，最后恢复。屏幕亮度以实际可读取的背光值或显示状态核对；不能只写“50%”。功耗采集及充电条件由本目录的功耗设计统一规定。

## 2. 顺序和次数

推荐把镜像阶段安排为 A → B → B → A。四阶段的 CPU 正式次数依次为 1、1、2、2，因此两侧各有 3 次。若设备起始处于 B，则可反转为 B → A → A → B，次数仍为 1、1、2、2。顺序在开始计分前固定，不根据分数调整。

优先让每次 CPU 正式运行来自不同的开机：后两个阶段中的第 2 次运行前增加一次同镜像正常重启。这样最低计划得到两侧各 3 个开机样本、3 个 CPU 样本，也能避免把同一次开机连续 3 次误称为 3 次独立板测。镜像切换后第一次开机的样本带 `post_flash_boot=true` 标签；统计时还需单列这一类样本，防止把一次性安装或优化开销混入稳定重启结论。

GPU 按同样的三个开机样本每侧各测 3 次，优先采用 Vulkan。若可用时间充裕，再增加 OpenCL 的同等重复次数。启动测量最低为每侧 3 次，优先提高到 5 次；CPU/GPU 不需要为了凑启动次数全部重跑。

每次性能运行前至少等待开机后 300 秒，同时核对后台任务和温度是否稳定。固定等待 60 秒不是充分的冷却条件。执行方在第一对样本前确定可达到的起始温度窗口，后续按相同传感器核对：配对样本的电池温度建议相差不超过 1 °C，已验证可读的处理器温度建议相差不超过 2 °C。若无法满足，保留样本并加“起始温度不匹配”标签，不删掉低分样本来让结果好看。

框架不得使用“温度必须低于 35 °C”等未经设备实测的固定门槛。执行方同时记录原始传感器名称、单位和缩放方式，避免把毫摄氏度和摄氏度混用。正式负载引起的后续降频是正常系统行为，必须保留；只有运行前已有不一致状态、应用失败或工作负载不完整才属于预先定义的异常。

## 3. 启动时长的定义

这次无外部仪器、无硬件改动的方案测量**正常重启到 Android 可用的时长**。它不等价于从完全断电到开机的冷启动；报告不能把 `adb reboot` 样本标成“冷启动”。

框架为每次启动同时保存以下终点，而不是用一个数字代替所有含义：

| 指标 | 起点与终点 | 能说明什么 |
|---|---|---|
| 控制端重启到连接恢复 | 控制端发出重启请求的单调时间，到第一次成功执行设备命令的时间 | 设备和传输路径重新可访问的时长；它不是 Android 启动完成时间 |
| 控制端重启到系统完成 | 同一起点，到第一次观察到本次开机的 `sys.boot_completed=1` | 包括重启、引导和 Android 启动的端到端代理值 |
| 控制端重启到桌面就绪 | 同一起点，到系统完成、用户已解锁、桌面活动处于前台并完成绘制的共同终点 | 接近用户能开始操作桌面的时长 |
| 设备内启动事件 | 本次开机可用的 bootstat、boot_progress 事件及设备启动后时钟 | Android 内各阶段耗时；它可能遗漏内核前及 XHyper 自身初始化 |

控制端每次用单调时钟记录命令发送前、返回或断开后时间。控制端经远程机器访问平板时，框架必须在实际运行 adb 的那台机器计时，不能把两台主机的墙上时间直接相减。时间线保留每次探测的发送与完成时间；重启前先记录旧 `boot_id`，恢复后必须确认 `boot_id` 改变，避免把旧连接误判为新启动。

`wait-for-device` 只用来确认传输恢复。它不表示开机完成，也不表示 root shell、桌面或存储已经可用。框架在恢复后以 1 秒左右的固定间隔读取少量属性；设备探测若超时，必须留下超时记录。检测终点用“上一次未满足条件”和“第一次满足条件”形成观测区间，报告同时给出实际轮询间隔与传输延迟。若 adb 在系统完成之后才恢复，终点只能作为上界；不能声称检测到了属性变成 1 的准确时刻。

桌面终点需要核对本机实际桌面包名、前台活动、解锁状态和首次绘制证据。`sys.boot_completed=1` 或 `mTopResumedActivity` 单独一项都不足以证明屏幕内容已可用。可用 boot_progress、窗口已绘制状态或可核对的 SurfaceFlinger 层时间作为辅助证据；命令和字段先在该设备验证，字段缺失时标记 unavailable。框架在终点之后再截图保存界面，避免每秒截图干扰启动。两侧使用相同解锁方法和锁屏设置；需要人为输入凭据的等待单独列出。

bootstat 和 logcat 的启动事件是辅助来源。框架读取设备实际提供的字段和当前开机时间线，不能根据通用 Android 源码假定厂商内核、引导程序或字段语义。引导程序提供的分阶段数值如可用，则原样保存并说明其起止点。Android 官方 bootstat 实现可供确认标准事件名称，但不能证明这台设备采用同一实现：[AOSP bootstat](https://android.googlesource.com/platform/system/core/+/master/bootstat/bootstat.cpp)。

## 4. Geekbench 6 CPU 与 GPU

### 4.1 工具与版本

两侧使用同一份 Geekbench 6 安卓安装包、版本和安装数据。现有 2026-10-05 的设备结果明确写着 `Geekbench 6.7.1`；本次执行仍需通过包管理器和结果 JSON 核对，不自动更新到其他大版本。官方记录表明 6.7.1 修复过 Android 上传连接问题，因此执行前应确认结果上传确实可行：[Geekbench 6.7.1 发布说明](https://www.geekbench.com/blog/2026/04/geekbench-671/)。

现有 `tools/perf/t11206-gb6-runs.sh` 可以参考按钮定位和环境快照，但不能原封不动作为本次功耗工作负载控制器。该脚本每 20 秒拉取历史数据库，还反复发送 `KEYCODE_WAKEUP`；它把历史数据库出现新结果的时间当成运行结束。现有 `gb6-history-dump.py` 仅解析 CPU，`gb6-compare.py` 的 noise 列只是两组内的分数范围，不能解释为置信区间。

框架用应用的实际界面和资源标识定位 CPU/GPU 按钮及 API 选项。平板没有可用触屏时，框架可以通过 adb、UIAutomator 或一次性输入点击完成控制，权限使用 `su 0`。框架不运行 `adb root`，也不凭已记忆的坐标盲点。执行前先采集界面结构，确认按钮、显示缩放和旋转方向。

### 4.2 运行状态与时间边界

每次运行都使用唯一 `run_id`，并采用下列独立状态：

`准备 → 启动应用 → 开始基准 → 正在计算 → 计算完成 → 上传结果 → 结果持久化 → 已导出`。

若应用上传失败，状态停留在“计算完成、未持久化”。框架保存截图、日志和已可取得的结果文件，继续其他项；不能将上传等待算入 CPU 计算时长，也不能立即 force-stop 丢失尚未保存的结果。达到预设上传等待上限后，把此运行标记为 `result_pending`，保存证据后再由执行方处理。所有失败和重试均有独立行，正式结果不能覆盖失败行。

首选读取本版应用实际提供的计算开始/结束事件日志。执行方先验证这些标记与界面状态的一致性，不能只按一条含有“benchmark”的日志猜测。若日志不能提供边界，使用事件驱动的 UIAutomator 状态观察；观察器以“正在计算”转到“上传”或“结果页”的事件为终点，不持续导出完整界面树，不反复唤醒屏幕。观察器必须原样用于双方，并把观察器的耗时和误差说明加入记录。

如果截止时间内只能实现稀疏界面探测，框架可以降级为固定低频率探测，但必须给出计算边界的区间和最大探测误差。此时不能把功耗积分宣称为精确覆盖了 CPU 计算阶段。框架可以额外报告“从点击启动到首次观察计算完成”的整段能耗，并说明其中包含的边界误差。功耗采样器不应因界面探测频率而改变采样节奏。

屏幕超时可在双方统一调长，以确保前台基准工作负载不中断；框架在开始前设置、完成后恢复。基准期间不发送 `KEYCODE_WAKEUP`，不执行完整 `dumpsys` 循环，不反复传输数据库、截图或结果。环境的完整快照放在工作负载开始之前和结束之后；运行中的少量温度、频率和功耗采样由统一的设备内采样器负责。

### 4.3 现有数据库已经能提供的数据

本轮只读核对过 2026-10-05 的历史副本，其模式包含：

```text
documents(id, type, description, json, created_at, updated_at)
cpu_documents(id, document_id, score, multicore_score)
gpu_documents(id, document_id, score, api)
```

其中 CPU 结果 JSON 已提供 `score`、`multicore_score`、`runtime`、`clock`、`valid`、`complete_benchmark`、版本、平台、选项及各子项。每个子项还包括 `factory_clock`、`workload_clock`、`runtime`、`runtime_warmup`、`runtimes`、`rate`、`work` 等字段。

一个已保存的样本内部 `runtime` 是 649.781161074 秒，旧脚本的同次完整等待记录是约 670 秒。这直接证明旧脚本等待时长不能代替 Geekbench 的内部运行时。框架应把内部运行时和控制端生命周期时长分别保存。`clock` 和子项时间戳目前只确认了字段存在，尚未确认其时钟域；框架不能未经校准把这些数值与设备启动后时间或功耗时间线相加。

若执行方需要子项级能耗，先用当前版的一次校准运行证明 `clock` 的时钟域，并确认能否通过实际计算进程的启动时间或事件日志映射到功耗采样器的单调时钟。无法证明映射时，仍导出全部子项分数、原始运行时和吞吐率，但只报告整次计算或已定义整段生命周期的能耗。不得凭 JSON 的墙上时间字段给每个子项构造假的毫秒级绝对时间。

结果数据库由一致性方法导出。若设备提供 sqlite3，则优先使用 SQLite 在线备份接口生成私有目录中的副本，再拉取副本；在线备份只在运行完成后执行。没有该接口时，先确认当前 JSON 已持久化，再停止应用，复制数据库及可能存在的 WAL/SHM 到同一快照目录；本地用只读连接读取并执行 `PRAGMA integrity_check`。不得在数据库仍写入时只 `cat history.db` 并把“没有新纪录”当成没有结果。框架还需保存数据库模式，确认当前应用是否发生模式变化。

每次导出使用开始前保存的最大文档号及结果 UUID/校验值筛选新增结果，再核对时间、类型、版本、`valid` 和 `complete_benchmark`。框架不能用数据库总纪录数推断运行成功；过往 CPU 历史和 GPU 纪录都可能增加总数。

CPU 导出总分及所有单核、多核子项，不只导出均值。GPU 导出总分、实际 API、设备名称、驱动/平台、所有 GPU 子项和可用运行时。`gpu_documents.api` 的整数语义必须从本版 UI 及成功结果 JSON 核对，不能在解析器中凭经验写死。两侧 Vulkan 只与 Vulkan 比较，OpenCL 只与 OpenCL 比较，二者不混算。

### 4.4 GPU 覆盖与快速补充

Geekbench GPU 项测量 GPU 计算工作负载；它不能替代图形渲染测试。官方提供了 GPU 计算工作负载说明：[Geekbench 6 GPU Compute Workloads](https://www.geekbench.com/doc/geekbench6-gpu-compute-workloads.pdf)。

本方案优先运行双方共同可用的 Geekbench Vulkan GPU 测试，每侧 3 次。OpenCL 作为补充独立列出，不强求在驱动不可用时通过其他软件绕过。框架要核对实际设备是硬件 GPU，不能接受软件渲染设备作为平板硬件 GPU 分数。如果某接口只在 B 失败，则保存错误和驱动日志，把它报告为功能差异；不能切换另一接口后把差异掩盖。

此次时间限制下，图形补充项优先使用同一份**设备内本地网页固定滚动与 Canvas/WebGL 动画负载**，避免安装大型基准及下载测试资源。页面文件、图片、字体、浏览器版本及浏览器设置固定，并保存文件哈希；页面从设备本地加载，正式工作负载不得依赖外网。框架每次清楚区分页面装载、30 秒预热和 120 秒正式窗口。两侧采用同一脚本生成相同滚动距离、速度、顺序和动画场景，不靠人工滑动。窗口大小、画布内部渲染分辨率及设备像素比固定。

本地网页输出 `requestAnimationFrame` 帧间隔的原始序列、实际窗口时长、完成帧数、平均帧率、帧间隔的中位数及第 95/99 百分位数，并在工作负载前后读取系统实际可用的帧统计。浏览器回调表示网页提交动画的节奏，不能直接当成屏幕实际呈现的帧数；系统统计也必须先确认对应的是网页窗口，避免把整个桌面的累计帧误计为网页帧。某接口只有短环形缓冲区时，最后一次读取不等于完整 120 秒记录。完整呈现统计无法取得时，报告只使用明确可得的网页帧间隔，注明这一边界。

本地场景属于图形与日常交互的综合工作负载，包含浏览器、CPU、GPU 和合成器的开销，不能给它命名为纯 GPU 性能。Geekbench 的 GPU 计算分数与这个场景分列。在简单场景已经达到屏幕刷新率上限时，平均帧率会隐藏性能差别；优先保留较重但可稳定重放的固定场景，并报告帧间隔尾部和能耗。复杂度在首次预检后固定，不能分别按 A、B 的分数调整。为解释掉帧而增加的完整系统跟踪应另做诊断运行，避免把持续跟踪开销混进主功耗样本。

如果设备已装好 3DMark 且测试资源齐全，可额外运行 **Wild Life Unlimited 的标准单次测试**，每侧 3 次。它的标准负载约 1 分钟，固定离屏渲染有助于避免分辨率和垂直同步上限掩盖差别，适合剩余时间充足时补充。执行前核对该设备实际支持 Vulkan 1.1、应用及负载版本。采集总分、平均帧率、每帧数据（若应用提供）以及结果页截图。相关定义来自 [Wild Life 官方说明](https://support.benchmarks.ul.com/support/solutions/articles/44002135593) 和 [系统要求](https://support.benchmarks.ul.com/support/solutions/articles/44002135597)。

如果已准备好的 Wild Life 不支持，则可用同样已经准备好的 Sling Shot Unlimited，固定同一接口和负载，保存图形子项分数。两侧都不能把 CPU/物理子项或 Sling Shot 总分冒充纯 GPU 分数。[3DMark 安卓测试说明](https://benchmarks.ul.com/3dmark-android) 提供了 OpenGL ES 3.0/3.1 的替代路线。框架不为这一可选项开启耗时安装下载，优先保证 Geekbench CPU、双方共同 GPU 接口、本地网页和规定功耗项。

若 Geekbench 的 GPU 接口都不可用，但 3DMark 可用，报告明确列出“Geekbench GPU 未完成，GPU 图形性能采用 3DMark”。不能把 CPU 跑分、界面滑动帧率或 GPU 使用率填写到 Geekbench GPU 分数栏。

## 5. 统计和有效性

每次运行保存原始值、镜像阶段、boot_id、应用版本、工作负载版本、起始与结束温度、电量、实际接口、设置快照、完整性状态和异常原因。CPU 总分、GPU 总分和启动耗时是预先定义的主要指标；全部子项是细分结果，不能从几十个子项里挑出偶然高低值当成总体结论。

报告每侧的样本数、独立开机数、全部原始值、平均值、中位数、标准差和最小/最大值。差值统一使用 `(XHyper / native - 1) × 100%`，并明确分数越高越好、时间和能耗越低越好。保留 0.1% 只是格式，不代表具有 0.1% 的分辨能力；启动时间应按实际观测区间给出可支撑的小数位数。

同一次开机连续运行的样本存在共同状态，不能作为独立开机重复。如果每侧只做到 2 个开机簇，报告给出簇内数据和簇间差异，置信区间标为探索性；不要以普通独立样本公式宣称小差别显著。若每侧取得 3 个以上不同开机、起始状态相近的有效 CPU 样本，可以额外对预先约定的配对分数比值取对数，按配对均值的 t 区间回算比例的 95% 区间，但仍声明样本很少、模型假设有限。区间跨过零或变化小于已观察离散时，结论写“本轮没有分辨出差异”，不能写“没有开销”。

等待上传失败、应用崩溃、GPU 接口不支持、开机超时、设置不匹配和功耗传感器失效必须逐条记录，不能变成 0 分、0 秒或 0 瓦。频率和热状态差异本身可能是被测系统行为；框架需区别“运行前人为不一致”和“同条件运行后自然变化”。

实现后必须用已知输入检查汇总器：旧 CPU 数据应能导出全部单核、多核子项与内部 runtime；故意缺少 GPU 纪录应显示 unavailable；重复 UUID、旧 boot_id、错误接口和不完整数据库均应被识别。无设备工作负载的采样开销核对与正常负载的阳性输入核对，属于测量工具校准，不需要反复开展产品测试。

## 6. 截止时间内的预算

旧数据只支持 CPU 每次整段约 670 秒的历史估计。本次 GPU、重启和温度恢复时间需要首轮实测校正，不预先承诺。

| 项目 | 初始预算 | 减少耗时的方法 |
|---|---:|---|
| 应用、能力、边界和结果提取预检 | 15–25 分钟 | 能力检查与采集框架核对一次完成，双方共用 |
| Geekbench CPU 双方各 3 次 | 67–75 分钟 | CPU 与该次功耗同步采集，不再为功耗单独重跑 |
| Geekbench GPU 双方各 3 次 | 15–30 分钟的预留 | 首次实际耗时校正后只保留共同主要接口 |
| 本地网页双方各 3 次 | 15 分钟正式运行及预热，另留装载时间 | 同一次固定日常负载同时测帧间隔和功耗 |
| 已准备的 3DMark 标准单次双方各 3 次（可选） | 6 分钟计算，另留启动时间 | 不安装下载，不运行 20 分钟 Stress 负载 |
| 至少 6 次启动及温度/后台稳定 | 30–45 分钟 | 启动计时与镜像切换、正式样本开机合并 |
| 结果提取与本部分核对 | 10–15 分钟 | 每次落盘后增量汇总，最后只查缺项 |

上述部分约需 145–205 分钟，其中部分环境等待可以与屏幕静置或规定的功耗稳定期合并，但不能把热机恢复期直接当成稳定待机样本。按 5 小时 30 分钟总窗口，剩余约 125–185 分钟用于镜像切换、静置/待机功耗和总报告。实际窗口缩短时，先取消 OpenCL、3DMark，再缩减本地网页重复次数及启动次数；CPU 和共同 GPU 接口的最低有效重复优先保留，启动最低为每侧 3 次。

执行框架以绝对截止时间安排：15:15 后只补主要指标的缺项，15:30 停止开启新的长基准，15:40 前固定结果集并生成报告，留出 20 分钟核对与交付。若预测某次完整负载无法在 15:40 前完成，框架在启动前跳过并写明原因，不能中断到一半后把部分运行当成完整分数。

以上设计已根据本工作区实际 Geekbench 脚本和 2026-10-05 的只读数据库副本核对；设备能力、当前版本、镜像身份、启动终点和功耗时钟映射尚未在本轮现场验证。
