# 镜像交付与测试执行交接

镜像负责方先交付原生与 XHyper 两个镜像清单，包含文件 SHA-256、宿主内核 SHA-256、运行时内核标识、Android 指纹、XHyper/管理器版本、构建配置、诊断开关、启动槽位和模式确认方法。清单格式见 `examples/image-manifest.json`。两侧内核、模块、Android 和测试应用必须相同；镜像差异只包含完成两种运行模式所需的部分。

测试执行方使用本仓库的协议及设备配置，先完成只读预检与传感器验证，再决定计量边界。镜像切换仍由镜像负责方处理。测试会话在每次重启和切换前告知设备使用者，切换后读回镜像身份和新的启动标识，再进入正式采样。

执行方优先采用 Perfetto `android.power` 和 `linux.sys_stats`，用官方 Trace Processor 导出。本机 PowerStats 示例服务的电源轨、消费者和状态驻留必须排除。启动先取已有 bootstat 与 logcat 记录，并保留控制端计时。细节见 `docs/MATURE-TOOLS.md`。

执行方需要在首轮完成以下适配。

1. 执行方核对桌面包名、用户解锁及首次绘制字段，确认启动终点的观察区间。
2. 执行方核对当前 Geekbench 的 CPU/GPU 按钮及 Vulkan 选项，并找到计算完成与上传开始的可信标记。
3. 执行方保存设置原值，统一亮度、刷新率、屏幕超时、网络、后台和声音，约定结束后恢复步骤。
4. 执行方验证电流单位、放电方向、更新率、累计电荷变化及外部输入是否实际断开。未知电源控制节点不能尝试批量写入。
5. 执行方检查本地采样器的开销和时间戳，并按已验证的供电分支配置功耗分析器。
6. 执行方验证待机端点和系统休眠证据。没有可靠的休眠证据时，结果使用“熄屏静置”。
7. 执行方在功耗窗口之外获取内存基线和完整进程统计，并要求镜像负责方交付虚拟化层保留内存的来源及范围。无法提供时，只比较 Android 可见内存，不推断虚拟化层独占量。

框架当前没有代替执行者实现界面观察、启动观察或电源恢复控制。上述适配完成后，按 `docs/PLAN-20261008.md` 的四阶段顺序执行，边运行边离线检查完整性。历史数据库可以用于测试导入器，但不能填入本轮正式结果。

最终报告使用统一差值方向，保留每侧全部原始值、独立开机数、供电边界、起止热状态、失败及缺项。报告应在 15:40 固定数据集，16:00 前交付；实际差异低于重复波动或计量分辨率时，写“本轮没有分辨出差异”。
