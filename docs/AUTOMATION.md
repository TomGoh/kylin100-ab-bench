# 串行自动测试入口

`suite` 在同一设备上顺序执行启动观察、环境与内存采集、亮屏静置、熄屏窗口、Geekbench 6 CPU/GPU、同步 Perfetto 和离线报告。`campaign` 调用镜像负责方交付的外部切换适配器，再分别执行原生 Android 和 XHyper 套件。本仓库不构建或刷写镜像。

截至 2026-10-08 13:10，完整单侧串行工具验证已经通过，记录见 [实机验收](VALIDATION-20261008.md)。本轮正式双侧 A/B 尚未执行，不能把历史分数或工具验证记录作为本轮对比结果。Geekbench GPU 测量计算性能；图形渲染和日常使用补充场景不在本入口的自动覆盖范围内，应单列完成状态。

## 可复制的命令

在仓库根目录执行，先将 `TP` 替换为已验证的官方 Trace Processor 可执行文件路径。`handoff/image-manifest.json` 和 `handoff/mode-switch.argv.json` 由镜像负责方交付；每次 `--out` 必须使用尚不存在的目录。以下是正式运行命令，须等当前设备验证及其他采集结束后使用。

```sh
cd /home/jose/xhyper-workspace/kylin100-ab-bench
TP=/absolute/path/to/trace_processor
python3 -m abbench validate-manifest handoff/image-manifest.json
```

设备已经运行对应正式镜像时，执行单侧套件。此命令请求三次正常重启；执行前会打印重启通知。

```sh
python3 -m abbench suite \
  --serial T11206HXH6600007 \
  --mode native \
  --out runs/formal-20261008-native-001 \
  --processor "$TP" \
  --profile profiles/t11206.json \
  --manifest handoff/image-manifest.json \
  --options examples/quick-coverage.json \
  --reboot
```

执行 XHyper 单侧时，将 `--mode` 改为 `xhyper`，另选新目录，并先由镜像负责方完成切换。单侧套件不能证明已经完成 A/B；缺少跨模式温度基线时，报告明确保留配对尚未验证状态。

外部适配器参数文件是 JSON 数组。例如，交付方按自己的真实程序及参数合同提供：

```json
[
  "/absolute/path/to/claude-image-switch-adapter",
  "--mode", "{mode}",
  "--serial", "{serial}",
  "--output", "{out}"
]
```

占位符只有 `{mode}`、`{serial}`、`{out}`。适配器须完成切换、重新启动及约定的恢复处理；它的输出参数目录不应占用套件随后需要新建的同名目录。框架以参数数组及 `shell=False` 启动程序，不解释 shell 管道或命令字符串。没有真实适配器时，不能自动双侧执行。

```sh
python3 -m abbench campaign \
  --serial T11206HXH6600007 \
  --out runs/formal-20261008-pair-001 \
  --processor "$TP" \
  --profile profiles/t11206.json \
  --manifest handoff/image-manifest.json \
  --adapter handoff/mode-switch.argv.json \
  --repetitions 1 \
  --options examples/quick-coverage.json
```

能解析但不满足合同的正式清单在调用切换适配器或设备之前拒绝，并生成失败报告；JSON 语法错误则由文件读取入口直接报错。切换返回零仍须通过新启动标识和设备身份核验；切换前后启动标识相同会拒绝进入套件。顺序先原生 Android、后 XHyper，再增加完整轮次。当前快速配置使用一轮，不承诺每侧三次 CPU/GPU。

工具验证须显式加 `--validation-only` 并使用独立目录。它跳过正式镜像合同门槛，报告和每个指标均标为 `validation`，不会与正式指标混算。验证模式不会缩短 Geekbench 的真实负载，也不能用短超时制造完整分数。命令返回零仅表示该入口记录的有效性通过；非零时检查失败及缺项，不能删除原目录后复用结果。

## 下午快速覆盖配置

[examples/quick-coverage.json](../examples/quick-coverage.json) 的目标是先取得双方主要项目，再利用剩余时间补充。启动和跑分次数按真实完成记录统计。

| 项目 | 每侧本配置 |
|---|---|
| 启动 | 三次实际新启动标识的正常重启；与完全断电冷启动分开。 |
| 开机稳定 | 最后一次启动的设备运行时间至少 300 秒。 |
| 内存基线 | 三个轻量快照，间隔十秒，另有功耗窗外的进程统计；三个同开机快照只是一份基线。 |
| 亮屏静置 | 请求 180 秒。 |
| 熄屏窗口 | 请求 300 秒；是否能叫待机取决于实际休眠证据。 |
| Geekbench CPU | 一次完整运行；计算阶段上限 780 秒。 |
| Geekbench GPU | 一次 Vulkan 完整运行；计算阶段上限 540 秒，硬件身份须通过。 |
| 持久化 | 每次跑分至多等待 90 秒；与计算阶段分别记录。 |
| 恢复及温度匹配 | CPU/GPU 前后各至少 60 秒恢复；每次温度匹配等待上限 120 秒。 |
| 界面观察 | 每 60 秒一次稀疏状态观察；两侧使用相同设置。 |
| 截止 | 2026-10-08 15:40（UTC+08），即 `2026-10-08T07:40:00Z`。 |

三次启动样本并不等于三次 CPU/GPU，也不等于三份独立内存基线。套件在最后一次开机稳定后采集一份基线；活动内存另随工作负载采集。正常重启终点报告系统完成的首次观察上界；可选桌面阶段仅是桌面活动恢复的代理，不声称首次绘制已经量出。

当前 `run_campaign` 在每侧切换前使用下面的保守预算，首轮正式模式启动项为 `3 × 180 + 300` 秒：

```text
亮屏窗 + 熄屏窗 + CPU 上限 + GPU 上限
+ 2 × 持久化上限 + 4 × 恢复时间
+ 2 × min(600, 温度匹配等待上限) + 1320
+ 正式启动项
```

代入快速配置为 `180 + 300 + 780 + 540 + 180 + 240 + 240 + 1320 + 840 = 4620` 秒，即每侧 77 分钟。1320 秒是编排器为环境、采集、分析等阶段保留的固定预算，不是已测耗时。外部适配器还有独立上限，默认 300 秒，会消耗同一截止余量；清理、恢复和报告也需要时间。不能把上述预算当作保证完成时间。

13:30 到 15:40 只有 130 分钟，少于两侧保守上限合计的 154 分钟。调度器逐侧准入：首侧实际较快完成、并在第二侧切换前仍剩超过 77 分钟时，才会启动第二侧；约 14:23 已是这项判断的边界，适配器消耗和后续步骤检查仍可能使第二侧缺项。若不足则保存 `deadline_insufficient_suite_coverage_budget`，不能承诺两侧必然完整。`minimum_suite_budget_s` 只允许增加门槛，降低它不能绕过计算出的保守预算。为 16:00 汇报预留二十分钟不代表清理一定在 15:40 完成。

请求更多轮次前应依据双方本轮实际耗时和剩余时间判断。不要为了凑三次分数缩短完整负载、降低准入门槛或把旧历史绑定为新结果。若时间不足，报告已完成的双方覆盖和全部缺项。

## 正式身份和共同条件

正式模式须使用完整双侧清单。`examples/image-manifest.json` 是故意未确认的模板，不能直接计分。双方的宿主内核摘要、运行内核标识、Android 指纹、Geekbench 版本及安装 APK 集合摘要必须一致；各自启动镜像摘要应对应其真实模式。XHyper 清单还须声明提交、管理器提交、正常构建配置和诊断功能，诊断配置单列，不计入本轮正常配置比较。

设备配置的 `identity_readback` 指定实际镜像路径、活动槽、运行内核标识路径和方法。当前配置的 `/dev/block/by-name/boot_a`、`_a` 及 `/sys/kernel/notes` 只适用于已核对的这台设备，不应照搬至其他平台。框架读回镜像 SHA-256、运行内核 notes SHA-256、指纹、槽和命令行，与当前模式清单逐项匹配；`kernel_runtime_id` 在这种配置下是 notes 的摘要。正式跑分还核对安装 APK 集合摘要，不能只用基础 APK 的摘要替代。

XHyper 必须有已配置且实际存在的正面运行标记。原生模式不得包含该 XHyper 标记；没有某标记本身不是不存在虚拟化层的证明，还必须有镜像负责方交付的模式来源和匹配镜像。模式标签不能代替读回证据；身份未通过时，较早采集的启动值也排除正式统计。

亮度、自动亮度、屏幕超时和插电保持唤醒须可读；缺失可选刷新率等设置保留限制。首侧稳定设置成为后侧共同基线，负载前核对已经恢复且设置相同。四十摄氏度是协议起始温度上限，不是厂商热保护阈值；两侧使用同一电池温度传感器，按配置的 1.5 摄氏度容差双向核对。快速配置最多自然等待 120 秒，不能达到共同条件则失败；保留原有调频和温控，不人为加热或关闭温控。

指标按应用版本、安装包摘要、API、实际设置、观察器配置和计量边界分别比较。实际温度保留为来源证据，不把每个温度值拆成不同统计组。一次 CPU/GPU 只能给出本次差异，不能估计重复波动或默认输出置信区间。

## 观察窗口和计量范围

CPU/GPU 启动前 Perfetto 保留至少两秒采样，终点观察后再保留至少两秒，然后停止并导出；请求窗口超出实际样本覆盖时拒绝计量，不静默裁短窗口。设备时间与启动标识共同约束窗口，不能跨重启积分。

每 60 秒的界面观察存在 ADB 和 UI 导出开销；实际间隔还包含命令耗时。两侧必须使用相同观察设置，指标保存观察器条件。没有独立证据时不估算、更不扣除这项开销。

只有实际观察到计算态、末次计算观察晚于启动点击、完成观察区间不超过 120 秒时，才使用“点击到观察计算完成上界”窗口。否则使用“点击到观察持久化”或导出完成的生命周期窗口，两类通过 `measurement_boundary` 分组。稀疏观察不能产生精确瞬时计算终点；Geekbench 内部运行时另存，不用上传或保存等待冒充计算时间。

每次跑分以开始前数据库文档号、新 UUID、完成状态和当前启动证据绑定，旧结果不得复用。SQLite 一致快照和完整 JSON、总分及子项均保留；GPU 还保存 API、设备及驱动身份，明确的软件实现拒绝，未知硬件身份排除正式 GPU 行。

当前 USB 仍供电，电池净电流及净能量变化不能作为整机功耗或续航。本机示例 PowerStats 服务的电源轨、消费者和驻留属于模拟数据，排除真实计量。未经验证的累计待机计量不能填零；没有实际休眠证据时仅报告熄屏静置。端点法包含终点查询和唤醒开销。内存只报告 Android 可见范围；采样最低可用内存不是实际峰值，`MemTotal - MemAvailable` 是估算不可用量，不是应用进程总占用。

## 排他执行、失败和退出

同一控制端的套件及活动按序列号取得非阻塞设备锁；另一入口立即失败为 `device_already_locked`。活动可在同一线程嵌套套件。该锁不约束其他主机、其他工具或显式单次 Geekbench/静置命令，持锁期间禁止其他会话操作设备、执行 ADB 或开始采集。

设备应预先完成应用首次授权。框架可处理普通无凭据锁屏；有凭据锁屏或未知界面不能通过猜坐标绕过。静置模块恢复自己修改的设置及原屏幕状态，并核对同一次开机。框架不修改频率、充电控制、热保护或未知电源节点。

运行目录保存 `suite.json` 或 `campaign.json`、逐步原始命令输出、结果文档、数据库、采集和报告。计算超时、离线上传或持久化失败保留原文及状态；缺失、无效和跳过有具体原因，不补零。采集停止和导出放在清理路径中，失败负载的采集仍尽力保留并分析。应用计算或保存状态不明确、或采集清理失败时，不再启动后续 Geekbench，也停止后续镜像切换。

需要中止时，先对当前入口按一次 `Ctrl-C`，等待有限清理和报告落盘。中止后不再调用下一侧切换适配器；已启动的外部程序如何安全回退仍由交付方合同约束。不要通过反复中断或强制杀进程跳过导出与设置恢复。若留下 `requires_device_idle_confirmation`，后续运行须先由执行方确认设备状态；不能直接重用目录或拿待保存结果计分。

截止值必须带时区。阶段、命令和轮询分别受预算约束，已超期完成的步骤不能交付有效指标。停止采集、导出和设置恢复有各自有限上限，可能越过总体截止；这不是硬实时退出保证。报告列出每侧真实启动数、完整跑分数、失败和缺项，最终有效性仍按各项证据判断。
