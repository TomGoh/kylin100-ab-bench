# 串行自动测试入口

`run_suite` 在同一台设备上顺序执行各项，复用启动观察、环境与内存采集、静置与待机、Geekbench、Perfetto 分析和报告模块。它不提供刷写实现。设备须已经解锁，应用首次运行许可已经确认，同一设备同时只能有一个执行入口；其他会话不得操作界面或开启采集。

```python
from abbench.suite import run_suite

result = run_suite(
    serial, "runs/formal/native-001", "native", processor_path, profile,
    manifest=image_manifest,
    options={
        "reboot": True, "boot_repeats": 3,
        "deadline_utc": "2026-10-08T08:00:00Z",
        "screen_on_idle_s": 480, "screen_off_standby_s": 900,
        "cpu_timeout_s": 1200, "gpu_timeout_s": 1200,
        "persist_timeout_s": 180, "recovery_s": 60,
        "max_start_temperature_c": 40.0, "cooling_wait_s": 600,
    },
)
```

每次目录必须新建。`validation_only=True` 跳过正式镜像合同核验，报告和所有指标的比较条件均标记为工具验证，不能混入正式对比。验证模式可采用十秒静置及待机窗；Geekbench 本身仍运行完整负载，不能靠短超时制造完整分数。单模式套件只能交付单侧材料，不能声称已经完成双侧测试。

套件及双侧活动按序列号取得同一控制端的非阻塞设备锁；另一个入口立即返回 `device_already_locked`，不会挂起等锁。活动入口可在同一线程嵌套单侧套件。此锁不控制其他主机、其他工具或显式单次 Geekbench/静置接口；持锁期间禁止其他会话执行 ADB。

## 顺序与身份

顺序为可选正常重启、开机稳定、环境及身份核验、三次轻量内存快照、亮屏静置、熄屏窗口、CPU、GPU。正式运行在本次开机至少 300 秒后开始；前后保留温度、后台和系统设置证据，保留系统原有温控。内存快照间隔十秒，进程内存辅助快照只放在功耗窗外；CPU/GPU 前后至少六十秒恢复，运行期间的内存由同次 Perfetto 采集保存。

正式模式必须通过现有双侧镜像清单验证，确认正常配置及双方共同内核、系统和应用身份。设备配置的 `identity_readback` 必须提供实际镜像路径、活动槽、运行内核标识路径和哈希方法：

```json
{
  "image_path": "/dev/block/by-name/boot_a",
  "slot_suffix": "_a",
  "kernel_runtime_path": "/sys/kernel/notes",
  "kernel_runtime_kind": "sha256",
  "mode_evidence_source": "cmdline",
  "mode_evidence_token": {"xhyper": "xhyper.mode=host", "native": null}
}
```

这些是设备适配字段，不能照搬为其他平台的事实。套件只读回配置路径的 SHA-256、活动槽、系统指纹和命令行，并与对应清单逐项核对。`kernel_runtime_id` 在这种配置下表示运行内核 notes 的 SHA-256。原生模式没有命令行标记时，必须依赖交付方清单中的模式来源说明和实际匹配的镜像哈希；缺少某标记本身不是没有虚拟化层的证明。Geekbench 成功后，正式分数还须核对安装 APK 集合摘要与清单匹配。完整结果、所有子项及拒绝原因均保留。

正式 XHyper 必须有已配置且实际存在的正面运行标记，原生模式不得包含该标记。环境控制的亮度、自动亮度、屏幕超时和插电保持唤醒须可读；未知可选设置保留限制。首侧稳定设置成为后侧基线，恢复后的工作负载环境须与该基线一致。指标比较条件携带实际设置；Geekbench 的功耗和内存也携带相同应用版本、安装包摘要和 API 身份。

四十摄氏度是本轮测试协议的起始温度上限，不是厂商热保护阈值。单模式以第一份稳定环境温度作为基线；活动入口将首侧基线传给其他模式，双方按同一传感器及配置容差核对。最多等待十分钟；过热或过冷均自然等待，不关闭温控，也不人为加热。不能达到共同条件时保留失败。单侧没有跨模式温度基线时，报告明确标为配对尚未验证。

## 窗口与失败

CPU/GPU 运行期间只启动一份设备本地 Perfetto，停止和导出放在 `finally` 中。跑分失败也尽力导出并分析这份采集，所有相关指标标为失败工作负载，不使用旧分数。计算仍在进行、结果仍待保存或采集清理失败时，不启动下一个 Geekbench。

计算边界需要实际观察到计算态，其末次计算观察须晚于启动点击，并且完成观察区间不超过 120 秒。满足时报告“点击到观察计算完成上界”窗口；不满足时报告“点击到观察持久化”的完整生命周期窗口。两者通过 `measurement_boundary` 分组，不混算。它们都不是经过校准的精确计算起止时间；界面观察开销也尚未独立量化，双方须使用相同观察器。上传和持久化时间不能伪装为计算时间。

GPU 结果必须通过硬件身份检查。明确的软件实现拒绝，未知硬件身份的原始计算分数保留并排除正式 GPU 指标。电池净电流/能量与整机功耗分别标记；当前 USB 外部供电状态下，套件不能给出整机功耗或续航结论。待机统计缺少实际休眠证据时降级为熄屏静置。累计待机端点包含终点查询及唤醒开销。

静置模块负责恢复自己修改的设置和原屏幕状态，并核对同一次开机。套件不修改频率、充电控制、温控或未知电源节点。失败、跳过、恢复异常和缺失计量保留在 `suite.json`、逐步原始目录和中文报告中，不补零。

`deadline_utc` 必须带时区。每步先检查保守预算，时间不足则明确跳过，已经超期返回的步骤不能交付有效指标。启动、环境和 Geekbench 均有命令与阶段上限；采集停止、文件导出和设置恢复必须完成有限清理，清理可能延伸到截止时刻之后，不能据此宣称按时完成了测试。调用者应为报告及清理预留余量。

## 双侧活动

```python
from abbench.suite import run_campaign

campaign = run_campaign(
    serial, "runs/campaign", processor_path, profile,
    manifest=image_manifest,
    adapter=["/path/to/image-owner-adapter", "--mode", "{mode}",
             "--serial", "{serial}", "--output", "{out}"],
    repetitions=1,
    options={"deadline_utc": "2026-10-08T08:00:00Z"},
)
```

镜像负责方提供适配器及其切换、回退和启动完成合同。框架仅按参数列表调用，不使用 shell；没有适配器时拒绝自动双侧测试。每次切换之后仍运行实物身份核验，不能把适配器退出零当作镜像正确。

本版适配器合同要求它完成切换和重新启动；前后启动标识相同则拒绝进入套件。全套预算按配置的窗口、阶段超时、恢复、冷却和启动数量计算，调用者指定的最低预算只能增加，不能降低这项保守预算。默认上限可能超出当天下午剩余时间，执行方需根据已验证运行时选定适当上限或明确接受缺项，框架不会保证无法实现的完整重复数量。

执行顺序先覆盖原生 Android 和 XHyper，再增加重复。正式活动默认首轮每侧采集三次真正的新开机，后续每阶段一次新开机。独立开机数量按实际启动标识统计；这些启动样本并不意味着 CPU/GPU 已有三次重复，跑分次数仍按完整运行分别报告。截止时间不足以增加重复时保留缺项原因，不能用采样点数替代重复次数。最终报告复用既有统计器，不生成默认置信区间。

测试入口：`python3 -m unittest tests.test_suite -v`。当前离线测试覆盖串行顺序、正式身份及活动槽拒绝、失败清理、截止预算、未知 GPU、工具验证标签和外部切换适配器。真实双侧活动仍须使用交付的两个镜像执行，本模块不会把工具验证记录当成本轮正式 A/B。
